# 25 — CI

Added 2026-10-08. Until then nothing ran this app's checks but a person on
their own machine. [02](02-architecture.md) asked for `core:doctor` to be
wired "into CI/deploy" before there was a CI to wire it into, and every
"Pest is green" in these docs is a sentence somebody wrote rather than a run
anyone can look up.

## What runs

`.github/workflows/ci.yml`, on every push to `main`, every pull request, and
by hand (`workflow_dispatch`). There are two jobs:

| Job | Steps |
| --- | --- |
| **Pest** | `composer install`, `npm ci` and `npm run build`, a `.env` from `.env.example` with a fresh key, `php artisan test --compact` |
| **Pint · audit** | `composer install`, `vendor/bin/pint --test`, `composer audit` |

Both jobs run on PHP 8.5, which is what `composer.json` requires ([24](24-php-85-and-core-08.md)).
Pint and the audit were both clean on the day the workflow was added.

## What it needs

**The `COMPOSER_GITHUB_TOKEN` Actions secret.** `uclemmer/laravel-core`,
`-postmaster` and `-ui` are private repositories pulled through `vcs` entries
([09](09-package-wiring.md)). The runner's own `GITHUB_TOKEN` reads only this
repo, so Composer needs a token with Contents: read on the `laravel-*` repos.
It is the same secret, under the same name, that the packages' own CI uses.
The first step of each job fails by name when it is missing, rather than
leaving Composer to fail inside the resolver with a message about a
repository it cannot reach.

The token is the owner's, so CI spends from the owner's GitHub API quota. A job
failing with "Could not authenticate against github.com" is usually that quota
running out, not a bad secret.

**A front-end build.** `public/build` is gitignored and the suite renders
pages carrying `@vite`, so the job builds the assets before testing. Without
them, every page test fails on "Vite manifest not found" instead of on what it
was testing.

## What it does not do yet

- **The suite runs on in-memory SQLite** (`phpunit.xml`), as it does locally,
  and has never run against the engine production uses. Raw SQL is the risk:
  the `LIKE … ESCAPE` fix ([23](23-like-escape-patches.md)) was green on SQLite
  and a syntax error on MySQL. `derby-days`' and `semperstat`'s workflows each
  run a database service and are the pattern for adding that job.
- **`core:doctor` is not run.** [02](02-architecture.md)'s step 5 still stands.
  It reads a real database and real configuration, so it belongs with the
  production-engine job above or with a deploy, not with the SQLite suite.
