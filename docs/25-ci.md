# 25 — CI

Added 2026-10-08. Until then nothing ran this app's checks but a person on
their own machine. [02](02-architecture.md) asked for `core:doctor` to be
wired "into CI/deploy" before there was a CI to wire it into, and every
"Pest is green" in these docs is a sentence somebody wrote rather than a run
anyone can look up.

## What runs

`.github/workflows/ci.yml`, on every push to `main`, every pull request, and
by hand (`workflow_dispatch`). There are two jobs, the first a three-row matrix:

| Job | Steps |
| --- | --- |
| **Pest · sqlite / mysql / mariadb** | `composer install`, `npm ci` and `npm run build`, a `.env` from `.env.example` with a fresh key, `php artisan test --compact` — once per engine |
| **Pint · audit** | `composer install`, `vendor/bin/pint --test`, `composer audit` |

Both jobs run on PHP 8.5, which is what `composer.json` requires ([24](24-php-85-and-core-08.md)).
Pint and the audit were both clean on the day the workflow was added.

## Three engines, until MariaDB is the only one

Added the same day. The suite runs on the in-memory SQLite it uses locally
(`phpunit.xml`), then on a MySQL 8.4 and a MariaDB 11 service container;
environment variables move it onto the service, since `phpunit.xml` forces
none of its values. Production here was written down as "MySQL/Postgres"
([02](02-architecture.md)). **The owner prefers MariaDB, and both server
engines stay in the matrix until every app is on it** — then MySQL leaves.

Raw SQL is why this matters: the `LIKE … ESCAPE` fix
([23](23-like-escape-patches.md)) was green on SQLite and a syntax error on
MySQL. No row is `continue-on-error`. The development machine has no MySQL or
MariaDB, so CI is the first place these rows run.

**What the first run found: one test, and no app bug.** `AudienceBuilderTest`'s
"dedupes by address when there is no account" inserted `Dana@Kenyon.example`
and `dana@kenyon.example` into the same fair's interest list. SQLite compares
those as different strings; MySQL and MariaDB compare under a case-insensitive
collation, so the `(event_id, email)` unique key refused the second row. Both
signup paths lowercase the address before `updateOrCreate`, and
`EventInterestTest`'s "treats addresses case-insensitively" holds that on every
engine — so the builder test now runs on SQLite only, where the database cannot
do the dedupe for it.

## What it needs

**The `COMPOSER_GITHUB_TOKEN` Actions secret.** `uclemmer/laravel-core`,
`-postmaster` and `-ui` are private repositories pulled through `vcs` entries
([09](09-package-wiring.md)). The runner's own `GITHUB_TOKEN` reads only this
repo, so Composer needs a token with Contents: read on the `laravel-*` repos.
It is the same secret, under the same name, that the packages' own CI uses.
The first step of each job fails by name when it is missing, rather than
leaving Composer to fail inside the resolver with a message about a
repository it cannot reach.

The token is the owner's, so CI spends from the owner's GitHub API quota. A job
failing with "Could not authenticate against github.com" is usually that quota
running out, not a bad secret.

**A front-end build.** `public/build` is gitignored and the suite renders
pages carrying `@vite`, so the job builds the assets before testing. Without
them, every page test fails on "Vite manifest not found" instead of on what it
was testing.

## What it does not do yet
